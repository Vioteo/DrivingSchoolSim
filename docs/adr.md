# Реестр архитектурных решений

Статус «принято для проектирования» не означает реализацию. Пересмотр: отдельный ADR с причиной, затронутыми контрактами и migration, старую запись не удалять.

## ADR-001 — Pure core и Unity adapters

Принято для проектирования; asmdef уже частично воплощают решение. Contracts/Simulation/Rules/Learning не знают Unity. Числовые расчёты можно тестировать без сцены; коллизии/физическое применение/рендер остаются в адаптерах. Отказ от одного большого MonoBehaviour уменьшает смешение UI, правил и динамики. Цена: нужны snapshots и явное управление tick. T07–T10; A06/A19.

## ADR-002 — Версия данных важнее удобного автодополнения

Принято для проектирования. Текущий world v1 поддерживается явно; следующий формат разрабатывается как отдельный DTO/version и migrator. Не добавлять curves/signals в v1 с ожиданием, что старый JsonUtility их сохранит. Неизвестная версия отклоняется до записи; исходник/backup сохраняются. Цена: миграционные fixtures и политики. T11/T15; A07/A10.

## ADR-003 — Один roadgraph, derived representation

Принято для проектирования. Mesh, AI и rules используют один compiled revision. Полосы/кривые и regulatory attachments имеют стабильные IDs; runtime editor не рисует независимую логическую дорогу. Цена: commit/invalidation pipeline. T11/T14/T16/T18; A07/A09/A11/A12.

## ADR-004 — Double canonical world и floating origin

Принято для проектирования. Сохраняем абсолютные double coordinates, 256-м клетки, локальные float в Unity. Отдельный origin service с fixed-boundary событием и аудитом потребителей. Не делать город гигантским монолитным mesh. Цена: streaming/origin consistency tests. T12/T13; A08.

## ADR-005 — Явная семантика ввода и безопасный FFB

Частично отражено в контрактах. Clutch=1 разомкнуто; requestedGear — выбранная передача, не increment. FFB normalized ±1 не Nm. Output.Stop идемпотентен; отсутствие устройства — штатный статус. Не смешивать вибрацию геймпада и wheel torque. Backend выбирается после hardware spike, а не из предположений о пакете. T04–T06; A04/A05.

## ADR-006 — Технический стенд, UI и физика принимаются отдельно

Принято для проектирования. IMGUI demonstration остаётся диагностическим; девять HTML screens — визуальный prototype, production UI — uGUI/TMP. Slider animation и программный lesson smoke не считаются ездой. Screenshot должен указывать renderer и revision. Цена: три отдельных доказательства готовности. T02/T03/T26; A02/A03/A19.

## ADR-007 — Калибруемая учебная динамика

Принято для проектирования. Начальный solver не обещает инженерную точность; коэффициенты/кривые и source calibration версионируются. МКПП/АКПП раздельны, assists отражаются в result. WheelCollider или собственные raycast contact adapters выбираются небольшой сравнительной проверкой перед T10; интерфейс сохраняет pure math. Нельзя менять модель контакта вместе с UI. T07–T10; A06.

## ADR-008 — Происхождение учебного контента

Принято для проектирования. Официальность определяется подтверждённым источником/редакцией/правами, а не названием файла и bool. Пока источник отсутствует, поставляются только авторские демонстрации. Нормы правил добавляются отдельными проверяемыми пакетами по юрисдикции. Цена: импорт и проверка provenance. T18/T22; A12/A17.

## ADR-009 — Desktop и XR имеют отдельные performance gates

Принято для проектирования. 1080p60 на Ryzen2700X/RTX2080 — desktop target; PCVR принимает нативный профиль конкретного HMD. Mirror quality/refresh/range профилируются отдельно. Mono mirror не выдаётся за stereo-ready. Цена: hardware evidence и отдельные настройки. T23–T25; A13/A14/A18.

## ADR-010 — Исходник ассета и проверка привязаны к хешу

Принято для проектирования. .blend — редактируемый источник, FBX/GLB — экспорты, prefab — интеграция. Каждый evidence указывает SHA256, exporter, renderer и сцену. Не использовать прежний общий PASS после изменения модели. Целевые бюджеты LOD не переименовываются в фактические без подсчёта импортированных треугольников. T02/T26; A02/A19.

## ADR-011 — Район собирается из модулей с семантикой, граф компилируется из раскладки

Принято для проектирования (24.09.2026). Модуль дорожного набора — это не только меш, но и **шаблон фрагмента графа**: полосы с осевыми линиями, связи полос внутри перекрёстка с зонами конфликта, стоп-линии, переходы, тротуары, места под знаки и светофоры, типы разметки между полосами. Раскладка района (JSON) перечисляет экземпляры модулей и их стыки по `Socket_*`; чистый компилятор проверяет стыки и собирает из шаблонов один граф v2. Граф — единственный источник истины (ADR-003): сцена, коллайдеры, ИИ, правила и маршруты строятся из него. Процедурные дороги по кривым не исключаются, но добавляются позже тем же графом. Цена: у каждого модуля два согласованных представления (меш и шаблон) — их расхождение ловит проверка генератора. [city.md](city.md); T27–T30; A07/A09.

## ADR-012 — ИИ-трафик кинематический, в координатах полосы (s, d)

Принято для проектирования (24.09.2026). Машины ИИ не используют физику колёс: состояние агента — полоса, пройденное расстояние `s`, **поперечное смещение `d` от осевой линии**, скорость, ускорение. Продольное движение — IDM; перестроение — плавная траектория `d(t)` в соседнюю полосу с решением по модели MOBIL; объезд препятствия — смещение внутри полосы или временный выезд в соседнюю/встречную полосу, если это разрешает разметка графа, с проверкой разрыва во встречном потоке. Восприятие — по проекциям всех участников (включая игрока, см. T31) на полосы, без raycast. В Unity агент — kinematic Rigidbody с коллайдером; столкновение с игроком останавливает агента и создаёт событие. Полная физика для ИИ не нужна: она дороже и хуже управляется правилами. Цена: игрока нужно привязывать к графу; занос и опрокидывание ИИ не моделируются. [city.md](city.md#ии-трафик); T16, T32–T35; A11.

## ADR-013 — Таблица ошибок экзамена как версионированные данные

Принято для проектирования (24.09.2026). Штрафные баллы берутся из одной таблицы-данных, перенесённой из Административного регламента МВД (приказ МВД России от 20.02.2021 № 80, **Приложение 5**) в **последней доступной редакции**; на 24.09.2026 это редакция от 26.05.2025 (изменения приказом МВД № 315). Каждая строка: шифр ошибки из регламента, текст, баллы, ссылка на пункт ПДД, редакция и дата сверки, источник. Константы штрафов в коде (`TrafficRules`, `SpeedLimitEvaluator`, курс площадки) заменяются ссылками на таблицу; игровые пороги (допуски, debounce) хранятся отдельно и помечены как игровые. Новая редакция регламента — новая ревизия пакета, старые результаты сохраняют свою ревизию. Цена: ручная сверка при каждой смене редакции. T37, T18; A12.

## ADR-014 — Единый диспетчер трафика

Принято для проектирования (24.09.2026), дополняет ADR-012. Всем движением в мире управляет один узел — `TrafficDirector` (pure C#), в Unity его обслуживает один MonoBehaviour `TrafficDirectorHost`. Диспетчер **владеет общим состоянием и порядком шага**:
- реестр участников: машины ИИ, пешеходы и игрок (игрок только читается, не управляется);
- все светофоры района: контроллеры фаз (T32) тикает только диспетчер;
- таблица резервов зон конфликта и переходов: разрешение на въезд выдаёт диспетчер, поэтому два агента не могут получить одну зону;
- появление и исчезновение агентов, плотность, пулы, связь с загрузкой чанков (T12);
- уровни детализации симуляции по расстоянию до игрока;
- seed и единый снимок состояния для представления, правил и отладки.

Решения отдельного агента (разгон, перестроение, объезд, поведение пешехода) остаются в отдельных модулях поведения (T16, T34, T17). Диспетчер вызывает их в заданном порядке и передаёт им один неизменяемый снимок мира на тик, поэтому результат не зависит от порядка обхода агентов. Так диспетчер не превращается в один огромный класс, а поведение тестируется отдельно. Правила ПДД читают тот же снимок, поэтому ИИ и оценка игрока видят один и тот же сигнал и одних и тех же участников. Цена: все участники проходят через один API, отдельные MonoBehaviour не принимают решений сами. [city.md](city.md#диспетчер-трафика); T35; A11.

## ADR-015 — Манёвры ИИ через разрешение диспетчера с уведомлением участников

Принято для проектирования (24.09.2026), дополняет ADR-014. Манёвр, который затрагивает других участников, машина ИИ или пешеход **не начинает сам**. Порядок такой: агент подаёт диспетчеру запрос → диспетчер проверяет конфликты по общей таблице резервов → выдаёт разрешение на ограниченное время или отказывает → **уведомляет затронутых участников**, и они получают конкретное указание (открыть окно, не начинать свой манёвр, снизить скорость). Разрешение выдаётся на ограниченное время: если манёвр не завершён вовремя, оно снимается, а агент выполняет заданный запасной вариант. Уведомления применяются на следующем тике, поэтому результат детерминирован и не зависит от порядка обхода.

Чтобы трафик не выглядел «телепатическим», уведомлённая машина реагирует только на то, что водитель мог бы увидеть сам: включённый поворотник, положение машины, аварийку. Поэтому запрос на перестроение подаётся вместе с включением поворотника, а реакция соседа начинается не раньше, чем поворотник горит заданное время (игровой параметр). Игрок запросов не подаёт. Диспетчер оценивает его намерение по поворотникам и траектории и создаёт за него «наблюдаемую заявку»: ИИ её учитывает ради безопасности и по правилам, а насколько охотно уступает — определяет профиль водителя. Цена: протокол запросов и уведомлений становится частью API диспетчера, и каждый новый манёвр описывается в нём явно. [city.md](city.md#разрешения-и-уведомления); T40; A11.
## ADR-016 — Настройки игрока: чистая модель + Unity-адаптеры

Принято для проектирования (24.09.2026). Новый asmdef `DS.Settings` (`noEngineReferences: true`, без ссылок) содержит `[Serializable] GameSettings` с вложенными группами `graphics`/`controls`/`audio`/`gameplay`, полями и значениями по умолчанию из `docs/ui-settings.md` §4, `int version`; `SettingsValidator.Sanitize` (clamp диапазонов, неизвестные индексы → default, NaN → default) и `SettingsMigrator` (цепочка v→v+1). В `Presentation`: `SettingsStore` (JsonUtility, `Application.persistentDataPath/settings.json`, запись через временный файл и замену, битый файл → defaults + warning) и `SettingsApplier` (Screen, QualitySettings, URP, камеры, UI-тема). Input получает мёртвые зоны/линейность как параметры от Presentation, а не ссылкой на `DS.Settings`. Не в `Contracts`: настройки — не порт между модулями симуляции, а состояние оболочки; Contracts остаётся набором DTO симуляции/правил/курса. Не `PlayerPrefs`: реестр Windows, нет версии и диффа. Цена: ещё один asmdef и ручное сопоставление JSON-ключей с полями (JsonUtility не поддерживает словари). T27; A03.
