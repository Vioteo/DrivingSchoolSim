# T26 — Манифест доказательств и валидация артефактов (Evidence Manifest & Verification)

- **Требования:** R15 (доказуемость на всех этапах M0–M3).
- **Критерий приёмки:** A19 (evidence manifest criteria).
- **ADR:** ADR-010 (привязка ассетов и кода к SHA256-хешам).

## 1. Конкретный результат и зависимости

Разработать утилиту верификации доказательств `tools/verify_evidence.py` и сформировать итоговый манифест доказательств `artifacts/reports/evidence-manifest.json`:
- Аудит целостности проекта:
  - Проверка физического существования всех файлов, на которые ссылаются `requirements.md`, `current-state.md`, `acceptance.md` и задачи `T01–T25`.
  - Вычисление и сверка SHA256-хешей для исходных файлов Blender (`ArtSource/*.blend`), экспортированных моделей (`*.fbx`, `*.glb`), архитектурных контрактов (`Contracts.cs`) и отчетов тестов (`editmode.xml`).
- Строгая классификация статусов:
  - `PROPOSED` (спроектировано): решение зафиксировано в ADR и документации.
  - `PREPARED` (подготовлено): ресурсы, примеры DTO или интерфейсы существуют.
  - `IMPLEMENTED` (реализовано): рабочий код присутствует в репозитории.
  - `VERIFIED` (проверено): есть воспроизводимый лог выполнения теста/команды именно для текущей ревизии с exit code 0.
- Правило инвалидации: изменение файла кода или ассета переводит зависимые пункты из `VERIFIED` обратно в `IMPLEMENTED` до нового прогона проверочной команды.
- Запрет фиктивных статусов: тест с 0 проверок или лог без маркера успешного завершения не может иметь статус `VERIFIED`.

## 2. Разрешённая область изменений

- `tools/verify_evidence.py` (новый скрипт валидации)
- `artifacts/reports/evidence-manifest.json` (выходной структурированный манифест)
- Файловый бюджет: 1 скрипт + 1 json манифест.

## 3. Точные входы, выходы и контракты

- **Входы:** Файловая система репозитория `DrivingSchoolSim`, логи в `artifacts/reports/`.
- **Выходы:** Манифест `artifacts/reports/evidence-manifest.json`.
- **Формат элемента манифеста:**
  ```json
  {
    "requirementId": "R01",
    "acceptanceId": "A01",
    "task": "T01",
    "status": "VERIFIED",
    "evidencePath": "artifacts/reports/editmode.xml",
    "fileSha256": "3e4b...",
    "verifiedAtUtc": "2026-09-19T06:45:21Z",
    "notes": "12 tests passed clean in batchmode"
  }
  ```

## 4. Примеры данных и ожидаемого поведения

- Запуск `python tools/verify_evidence.py`:
  - Обходит ссылки из документации.
  - Для `R05 / A02 / T02` находит `DS_Sedan_A.fbx` и отчет `sedan-fit.json`.
  - Для `R15 / A01 / T01` находит `editmode.xml` с 12 пройденными тестами.
  - Для неподтвержденных аппаратных требований (G27 FFB, VR HMD) выставляет честный статус `NOT_RUN` / `BLOCKED: No physical device`.

## 5. Отрицательные сценарии

- **Битая ссылка на файл:** Если в отчете указан несуществующий файл доказательств, валидатор завершается с ошибкой и маркером `BROKEN_EVIDENCE_LINK`.
- **Несовпадение контрольной суммы:** Если модель была переэкспортирована, а хеш в манифесте остался старым, статус инвалидируется с требованием повторной проверки.
- **Поддельный PASS:** Лог, содержащий `failed="1"` или завершившийся по таймауту, не может получить статус `VERIFIED`.

## 6. Команда проверки и доказательства

```powershell
python tools/verify_evidence.py
Get-Content artifacts/reports/evidence-manifest.json | ConvertFrom-Json
```

## 7. Условия завершения

- Создан скрипт `tools/verify_evidence.py`.
- Сформирован актуальный манифест `evidence-manifest.json` с честным разделением статусов (без неподтвержденных PASS).
- Манифест подтверждает целостность всех ключевых артефактов проекта.
