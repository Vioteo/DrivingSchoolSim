# План реализации и передачи

Связи требований R01–R15 находятся в [requirements](requirements.md), критерии A01–A19 и команды C00–C05 — в [acceptance](acceptance.md), конкретные задания T01–T26 — в [индексе карточек](tasks/README.md). Всё, кроме отмеченного в current-state, — план. Оценок сроков и обещаний готовности hardware здесь нет.

## Этап M0 — ревизия модели, UI и исполнимый каркас

Сначала завершить текущую cabin-v3 через отдельный арт-процесс, принять каждый изменённый узел по реальным рендерам; не перезапускать старый генератор поверх принятого shell repair. T02 фиксирует проверяемый asset manifest и import validation, не меняет художественную модель. T01 закрывает compile/test/prepare baseline, T26 проверяет evidence. HTML UI принимает отдельный UI-исполнитель; T03 переносит по одному согласованному экрану в uGUI/TMP.

Переход: неизменяемая baseline-ревизия с известными ограничениями, actual hashes, screenshot sources, NUnit report и воспроизводимым import/build либо явно указанным blocker. Не требовать реальную езду для приёмки визуального прототипа; не объявлять поездку готовой на основании прототипа.

## Этап M1 — одно управляемое учебное движение

T04 keyboard command → T07 numeric validation/engine → T08 clutch → T09 gearbox → T10 Unity physics adapter. Выбрать contact approach коротким сравнением на одинаковой плоскости/наклонной; записать ADR до реализации всей динамики. Добавить T05 G27 calibration и T06 FFB, но keyboard путь должен оставаться работоспособным без оборудования. T20 укрепляет существующий start-stop session и result; T21 первым экземпляром делает startstop evaluator. T23 готовит desktop зеркала; T03 подключает только реальные состояния.

Переход: на малой площадке работает keyboard drive, start/stall/manual shift/reverse/brake/stop, результаты занятия объяснимы, проигрывается фиксированный input trace. A04–A06 и первая часть A16 имеют evidence. Hardware-specific подпункты могут оставаться BLOCKED при отсутствии устройства; они не считаются закрытыми.

## Этап M2 — данные, редактор, мир, участники и обучение

T11 сначала утверждает v2 graph и migration fixtures. T15 сохраняет/восстанавливает версии. T14 добавляет команды редактора по одной, каждая меняет тот же graph; из него строятся mesh/collision. T12 chunk lifecycle предшествует T13 floating origin. Для проверки 10×10км использовать synthetic world, прежде чем наполнять город артом.

T16 и T17 добавляют один тестовый intersection с автомобилем и пешеходом. T18 вводит одно семейство правил за итерацию и подключает доказательства в result. T19 отдельно вводит surface physics и затем weather presentation. T21 выполняется для восьми конкретных IDs, T22 добавляет авторскую теорию и доверенный импорт. Городской маршрут расширяет набор занятий отдельно от восьми упражнений площадки.

Переход: A07–A12, A15–A17 покрыты маленькими fixtures и integrated route. Наличие схемы города не заменяет streaming, а трафик на waypoint animation не заменяет lane/conflict behavior.

## Этап M3 — XR, качество и подтверждение производительности

T24 запускается после desktop correctness и T23: OpenXR rig, отдельная проверка input/UI, затем stereo mirrors. T25 измеряет desktop1080p60 на заданном PC и отдельно профиль выбранного HMD. Полировка LOD/culling/RT update выполняется по конкретным bottleneck данным, по одному изменению на повторный benchmark. Hardware gates требуют физические устройства.

Переход: A13/A14/A18 с указанными средами/настройками, пройдены lifecycle unplug/pause/quit, нет незадокументированных отключённых features ради FPS. Окончательная версия content/rules/asset согласована и все доказательства проходят T26.

## Как выдавать малую работу

Один запуск исполнителя получает одну карточку и **одну итерацию**, если карточка повторяемая. Контекст: сама карточка, перечисленные исходники, относящийся абзац формата/ADR и один критерий приёмки. Не передавать всю историю проекта. Бюджет изменения обычно ≤3 production files плюс один тестовый файл и evidence; если задача требует больше границ, сначала разделить её и обновить индекс, не начинать большую перепись.

Вход должен указывать текущий asset/code revision и незакрытый критерий. Выход: diff, exact commands, reports, negative case, оставшиеся ограничения. Нельзя закрыть семейство повторяемых задач по первой итерации. В первой строке итогового отчёта писать «Txx, итерация <конкретное действие>», чтобы следующий исполнитель не повторял работу.
